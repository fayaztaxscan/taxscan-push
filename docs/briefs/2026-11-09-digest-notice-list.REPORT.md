## For planning to read first

1. **What a new (imported) suppression row changes in the audience writer and the digest send, exactly (proved in `audienceStatusImport.test.ts`, against the fake Mailercloud):**
   - **The digest send: nothing.** The digest send never reads `EmailSuppression`: only the Mailercloud webhook, the writer, ingest and the pull do (a source-scan test over `src/services/digest` and `src/routes/digest*` pins it). Who receives the paid digest is decided by Mailercloud's segment, which already excludes these contacts. The send guard's `pending_writes` check does not read `suppressed` either, so it is unchanged.
   - **The writer, on the imported members:** a new or escalated row goes through `afterSuppressionWrite`, exactly like a webhook opt-out, so the member becomes `suppressed` and due. Its next tick then makes **no contact call and no write**: the only request is the writer's usual read-only tag-name search (`POST /v1/tags/search`, made at the start of any tick with a due member). An already-tagged reader keeps its Premium tag and role. A never-tagged reader is never tagged (adds stop for a suppressed member; they are unsubscribed in Mailercloud anyway).
   - **One bookkeeping change worth knowing:** a **refused (FATAL) reader whom the file lists as bounced or unsubscribed has its FATAL flag cleared** by that tick (the writer records "done" because there is nothing left to write). The Audience card's **refused count (today 78) therefore falls**, **Retry refused** no longer includes them, and their `audience_writer_fatal` noise stops. They stay on the notice list: the reason then comes from the suppression row (`bad_address` for a HARD_BOUNCE row). A refused reader the file does **not** list as bounced is left exactly as it was (tested). The nightly full load would flip `suppressed` for any suppression row anyway (ingest recomputes it), so this is the existing mechanism, only sooner.
   - I did not stop: nothing about who receives the digest changes. If you want the refused count preserved, say so (it would need a change in the writer, out of this brief).
2. **The list reads only `status = 'active'` accounts (the brief's rule).** The paid digest goes to PREMIUM = active **or cancelled-but-still-paid** (`memberRole`), so a cancelled-but-paid reader whose address bounces gets **no notice**. One line in `digestNoticeList` adds `cancelled`; say if you want it.
3. **Only addresses a CMS account holds are written by the import.** Mailercloud's export is its whole contact book (the hand-made digest's ~5 lakh contacts); writing them all would put hundreds of thousands of rows in `EmailSuppression` no reader of ours uses. Every other address is counted as `notInCms` and left alone. So the reply has one count the brief did not list (`notInCms`): `{ read, invalid, ignored, notInCms, matched: {UNSUBSCRIBE, HARD_BOUNCE, SPAM}, created, upgraded, unchanged }`.
4. **I could not see a real Mailercloud export, so its header names are assumed.** Accepted (case and `_ - .` ignored): email: `Email`, `Email Address`, `Email ID`, `E-mail`, `Mail`, `Contact Email`; status: `Status`, `Contact Status`, `Subscription Status`, `Subscriber Status`, `State`. Statuses: `Unsubscribed`; `Hard bounce` / `Hard bounced` / `Bounced` / `Bounce`; `Spam` / `Complained` / `Complaint` / `Spam complaint`; everything else ignored. A file whose headers differ is a plain 400 naming what was looked for and writes nothing, so a dry run with Anagha's real file costs nothing. Worth doing before the owner relies on it (it also shows whether the 78 refused appear as "Hard bounce").

## What it does
- **`digestNoticeList(portal, now)`** (`src/services/audience/notices.ts`), the single definition (the door, the Audience card and the tests all read it): one row per CMS account; `bad_address` = the writer's FATAL or a HARD_BOUNCE suppression (wins); `unsubscribed` = an UNSUBSCRIBE suppression; suppressions joined by address hash **or** account id; never SPAM / MANUAL / ACCOUNT_DELETED, consent = false, a non-PREMIUM member, or an account not live / with no address; sorted by account id, so the ETag (sha256 of the items) is stable. Two accounts that share an address both appear.
- **Door N**, `GET /api/integrations/cms/digest-notices` (`src/routes/cmsNotices.ts`, mounted before door W's router because that one ends in a catch-all 404). Order: flag (off = 404, before anything is read) → IP fence (`cmsClientIp`, never `req.ip`; empty = reject all) → 30 requests an hour per client (429; only a fenced client reaches it) → no body, both headers, the signature over the CONSTANT path (±300 s, current or previous `CMS_FEED_NOTICES_SECRET`), a SIGNED `nonce` and **no other query parameter** → nonce spent (single use, 10 minutes) → freshness (**503 `{"error":"not_ready"}`** with no COMPLETE full load in 48 h or the breaker open, checked before a 304) → the list built on request: `If-None-Match` = ETag → 304, else 200 `{ as_of, portal, count, items: [{account_id, reason}] }`. Every failure of the fence, signature and nonce is the same `401 {"code":"UNAUTHORISED"}`; the log gets a step code only. An empty list is a real 200 `count: 0`.
- **Import** `POST /api/digest/audience/import-statuses` (ADMIN, cookie only; raw CSV ≤ 5 MB; works whatever `DIGEST_NOTICES_ENABLED` says): reads the CSV with a small dependency-free parser (quotes, CRLF/LF/CR, BOM, comma / semicolon / tab); only CMS-held addresses; an upsert on `emailHash`, `source = 'mailercloud_export'`, with the existing `SUPPRESSION_RANK`, written **only when the incoming reason strictly outranks the row's** (so a re-import changes nothing, not even `lastSeenAt`, and MANUAL is never touched); new or escalated rows go through `afterSuppressionWrite`. Addresses are normalised and hashed and never logged, audited or returned: the reply, the log line and the `AUDIENCE_STATUSES_IMPORTED` audit entry are counts only (a scan test checks the reply, the logs and the audit row for every address and hash). Bad files are plain 400s: `empty`, `too_big`, `not_csv`, `no_email_column`, `no_status_column`.
- **Audience card (ADMIN):** `notices: { enabled, ready, badAddress, unsubscribed, asOf }` in the payload (PUBLISHER gets none); the screen shows the counts line, one muted sentence when the door is off or not ready, and the import button.
- Boot line `[audience] digest notices on|off ...` (names, never values); `CMS_FEED_NOTICES_SECRET(_PREVIOUS)` are masked in logs like the other door secrets and must differ from every other door's secret.
