# Brief: Reads from the CMS (Feed 2) replace GA4

- **Date / name:** 2026-10-29-cms-reads → branch `build/cms-reads`, base `origin/develop`
- **Standing rules:** `docs/briefs/BUILD-SESSION.md` (read first)

## Goal
A flag-gated sync mirrors the CMS's **Feed 2** (per-article views per IST day) into our Postgres. When a second
flag is on, every place we show or use **reads** takes CMS numbers for dates from the CMS start date, and GA4 only
for older dates, labelled as such. GA keeps syncing as it does today.

## Why (owner's words)
> 2026-10-29: "In the campaign report, currently read column is from google analytics. But this number is not
> correct after implementing DPDP act in new cms. Can we read that number directly from cms?" On scope, "go with
> recommendation": everywhere reads are shown. The owner confirms the CMS's counting doesn't depend on the
> consent banner, which is why we're moving.

Since the new CMS's consent banner (29 Sep), GA4 sees about 1 in 10 readers (memory: GA reads).

## Scope
**In:**
1. **Storage:** a new table, e.g. `CmsArticleView` (`portal`, `articleId`, `canonicalPath` = the path of
   `canonical_url`, `externalId?`, `date @db.Date`, `views`, `pushViews?`, `digestViews?`, `cmsUpdatedAt`,
   `fetchedAt`), unique on (`portal`, `articleId`, `date`), with indexes for the readers below. Additive migration.
   Nulls stay null.
2. **Client + sync:** reuse the `cmsClient` signing / https / host allowlist / `redirect: 'error'` / timeout / retry
   machinery with a new secret `CMS_FEED_VIEWS_SECRET` (≥ 32 chars, in `logSecrets()`, never logged). Routine run
   every 2 h: `from = today − 2` … `to = today` (IST), **no `published_since`** (Reports needs old articles too), all
   pages; upsert. A day with no rows must not delete anything. One log line per run (rows, pages, ms, as_of). A
   failure or an incomplete page chain **writes nothing for that run** (same rule as GA reads, PR #74) and raises
   one alert per IST day via the existing alert path.
3. **Backfill:** `npm run cms-views:backfill -- --from 2026-09-28 [--to …]`, in 30-day chunks, idempotent.
4. **One reads module:** a single function family, e.g. `src/services/reads.ts`, that every reader calls, so no
   screen mixes sources ad hoc. It returns views and push-views per article path per date range, choosing **CMS for
   dates ≥ `READS_CMS_FROM`** (default `2026-09-28`) **and GA for dates before**, and reports per result which source
   or sources it used. When CMS `push_views` is null (before 15 Oct), push-views come back as "unknown", not 0.
   **Matching a campaign or feed URL to a CMS row:** by `canonicalPath`. Then, for migrated stories, by the old
   trailing numeric id = `externalId`, reusing `readsPath()` / `articleKey()` logic. Explain your matching in the
   REPORT, with a count of matched/unmatched against the fixtures.
5. **Switch the readers to it**, all behind `READS_SOURCE=cms` (default `ga` = today's behaviour exactly):
   - Campaigns: Reads + via-Push columns (`listCampaigns` in `src/services/metrics.ts`). Keep "—" = no data ≠ 0.
   - Reports → Reads tab (`src/services/readsReport.ts`, the `GaReadsReport` cache build) and
     `readsSummaryForWindow`.
   - The coverage email's "How it was read" section.
   - The digest builder's ranking input (`src/services/digest/readsSource.ts`, the organic read rate). With CMS:
     organic = `views − push_views − digest_views` when both are known, else `views`. State this in the REPORT.
6. **Labels:** wherever reads are shown, a small source note: "Reads: CMS" / "Reads: GA4 (≈1 in 10 readers since
   29 Sep)" / "Reads: CMS from 29 Sep, GA4 before". Use the screens' existing muted-note style. Reports PNG/share
   images include it.
7. **Admin guide:** one short paragraph (reads come from the CMS; GA only for older history). Bump the version line.
8. **Retention:** the table grows by ~thousands of rows a day. Note the growth and the index sizes from your 85k-row
   fixture in the REPORT. No sweeper in this brief.

**Out:**
- Stopping the GA sync, or removing GA code.
- Search Console / Surfaces (a different metric; untouched).
- Any CMS-side change. Any production call.

## Flags / env (all default off or today's behaviour)
`CMS_VIEWS_ENABLED` (sync cron + backfill allowed; off: boot line `[cms-views] disabled …`),
`READS_SOURCE` = `ga` | `cms` (readers), `READS_CMS_FROM` (default `2026-09-29`), `CMS_FEED_VIEWS_SECRET`. The views
path (`/api/v1/push-feed/article-views`) uses the existing `CMS_FEED_BASE_URL` host rules.

## Acceptance tests
1. Fake CMS, A.8 fixtures: multi-page pull upserts every row; rerun = no change; a 500 mid-chain, a never-ending
   cursor and a bad row each write **nothing** and raise one alert; a signed request uses the V secret and is
   refused with the L secret (and vice versa: our client never sends the L secret to this path).
2. Nulls: `push_views` null before 2026-10-15 stays null and shows as unknown (not 0) on Campaigns.
3. `READS_SOURCE=ga`: every reader's output is byte-identical to today's (snapshot the existing tests).
   `READS_SOURCE=cms`: a campaign whose article has CMS rows shows CMS numbers. A range spanning `READS_CMS_FROM`
   sums GA before + CMS from, and is labelled as both.
4. Matching: canonical path match; a migrated story matched via `externalId`; an unmatched URL shows "—".
5. Digest ranking with CMS input: organic rate as defined above (unit).
6. EXPLAIN on 85k `CmsArticleView` rows for the Campaigns sum and the Reports window query: index scans. Paste the plans.
7. Browser, one at a time: Campaigns and Reports → Reads with `READS_SOURCE=cms` against seeded fixture rows show
   CMS numbers and the source note. Screenshots in the REPORT.
8. tsc, lint (0 errors), `npm run build:admin`, the full suite: green.

## Constraints
- **The request path never calls the CMS** (same invariant as GA reads): crons fill Postgres, requests read Postgres.
- Never log a secret, a signature or a full signed URL. Use `safeErrorLog` (`src/lib/httpErrors.ts`).
- The `rolled + live` rule is about `Event` and doesn't apply here, but keep **one** reads implementation
  (item 4). Don't add a per-screen query.
- No new dependency.

## CMS answers (29 Oct, CMS planning session)
- History exists from 2026-09-28, but **28 Sep is partial** (taxscan.in switched over at ~22:00 IST that night).
  Hence `READS_CMS_FROM` defaults to **2026-09-29**: GA covers all of 28 Sep, CMS from the first full day. The
  backfill still accepts `--from 2026-09-28` (the rows are stored; the reads module just doesn't use them by default).
- 29–30 Sep raw traffic was ~70% robots; the CMS rollup filters them, so those days come out far below the raw
  counts. That's correct; don't "fix" it.
- Endpoint ETA ~4–5 Nov, if the owner approves the CMS's combined Feed 1 → Feed 2 brief. Build against fixtures regardless.
