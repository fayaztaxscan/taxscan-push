## How matching works (acceptance 4), with counts

A requested taxscan path is matched to CMS rows **first by `canonicalPath`** (the path of the CMS's `canonical_url`, trailing slash dropped: a migrated story keeps its old address, so its path is the same), **then by the old trailing numeric id** (`-<4+ digits>` at the end of the slug, the same rule as `articleKey()`) equal to the row's `external_id`. A row reached by both counts once. No match from either source → the path is absent from the result → "—", never 0.
Counts against the fixtures (`readsCms.test.ts`, six campaign paths, `READS_CMS_FROM=2026-09-28`): **5 matched, 1 unmatched** (4 by canonical path, 1 by `external_id`: a pushed URL with an old slug whose CMS row has a new slug but the same id; the unmatched is a story nothing has counted). In the browser seed: 4 of 6 campaigns matched in the CMS (one by id), 1 more got GA numbers only from before the cut-over, 2 showed "—" (an academy link and a story with no rows).

## Source rule and the unknowns

- **Dates:** with `READS_SOURCE=cms`, dates `>= READS_CMS_FROM` come from the CMS and earlier ones from GA4; a range spanning the date sums both and says so. 28 Sep is **stored but not used by default** (the CMS marks it partial): an edge-case test shows GA's number winning for that date, and the CMS one used only if `READS_CMS_FROM=2026-09-28`.
- **Push-views unknown, not 0:** a result is `pushViews: null` (shown as "—" with a tooltip on Campaigns) whenever **any** contributing CMS day has a null push count (i.e. before 15 Oct); a real 0 stays 0. GA's push numbers are known. In the email's "via push" total an unknown day contributes nothing and the note says it counts from 15 Oct.
- **Digest ranking (organic reads), as the brief asks me to state:** per CMS day row, `organic = views − push_views − digest_views` **when both are known, else `views`**, clamped ≥ 0 per row, summed over all dates. An article is matched by its path(s) or the id in its key (`article:<id>` = `external_id`). The source is "not fresh" (the builder then ranks newest-first, as with GA) when the sync is off, has never written, or last wrote > 6 h ago.
- **Reports → Reads in CMS mode** (a different shape from the other readers, because that tab is built from the GA Data API, not from `ArticleReadStat`): each trailing window = GA for the days before the cut-over (still the Data API, in the daily cron, never a request) + the CMS rows from Postgres from the cut-over on, merged per article path. The CMS feed has **no headlines**, so a story GA never saw is classified from its slug (`titleFromPath`, as the email already does): coarser content-type detection, same bench/category rules; a CMS row is an article by definition, so GA's "numeric id" filter is not applied to it (new-CMS stories have no id in their address). The CMS has no site-wide total, so `siteViews` there = GA's site total for the pre-cut-over days + the CMS article views (the UI does not show it). The cache row now carries `source`; the route never serves a build of the *other* source (it answers `ready:false` "being rebuilt…") and the boot pass rebuilds on a mismatch, so flipping the flag cannot leave a GA table under a CMS label.

## Worth remembering

- **Unverified against the real CMS** (it does not exist yet, ETA ~4–5 Nov): the cursor format (treated as opaque; the client only needs a non-empty string and refuses a repeat); how many rows the routine 3-day window with no `published_since` really returns (it may be tens of thousands, ~5–10 pages of 5,000; the client caps at 400 pages and the write is one transaction with a 120 s timeout); `to ≤ today (IST)` is satisfied (we send IST today); a CMS `429` (120/min bucket) is retried with backoff.
- The CMS rollup recomputes **today, yesterday and (at 00:07 only) the day before**, so the routine window of today − 2 … today is exactly the set that can still change; older days are final after D+2.
- A day with no rows for an article has no row: an article that stops being read simply stops accumulating, and one the CMS takes down drops out of the feed but **its stored rows stay** (we never delete on absence).
- `GA keeps syncing` as asked; nothing in `gaReads.ts` changed. Surfaces / Search Console are untouched (they only import `readsPath`, now via the re-export).
- To switch on (planning's decision, not done here): set `CMS_FEED_VIEWS_SECRET`, `CMS_VIEWS_ENABLED=true`, run `npm run cms-views:backfill -- --from 2026-09-28 --yes` once, check the first `[cms-views] synced …` line, then `READS_SOURCE=cms` (the Reads cache rebuilds at boot).
