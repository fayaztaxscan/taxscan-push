The guard below supersedes the first "Worth remembering" bullet and the "do not unset" warnings of the first build (replaced in the docs and `.env.example`, see below).

### What it does
- **Workers (LinkedIn and Facebook).** A today's-rule candidate (an article's oldest push) is skipped when ANY push of the same article already has a `push:` row on that page, whatever status the row has (POSTED, FAILED, SKIPPED, in flight). While reading the campaigns the worker also records, for each of today's-rule articles, the id of every push of that article in the same read (`idsOfArticle`); after the page's one `have` read it takes the campaign ids out of the `push:` keys (`pushedCampaignIds()`, the id sits in the key) and drops every candidate whose article has one of them. **No extra query**, the read stays `select`-narrow, and with no `push:` row on the page nothing changes (every existing test passes unchanged).
- **Screens.** An article row of today's rule that has no article-key row now shows the page's `push:` row of its own push, else the latest `push:` row of the article's other pushes, so it never reads WAITING while the worker skips it; the row carries that push row's id, so Retry and Skip act on it. One combined read (`OR`), no extra query; an article-key row still wins. If the same campaign row was sent again and so has two `push:` rows, the later one (by creation time) shows, so the choice never depends on the order the database returns them.
- **Campaigns Channels.** An article push's mark falls back to ITS OWN `push:` row when there is no article-key row, else to the latest row among the article's other pushes in the same list (a repeat, or the oldest push, of an article the new rule handled), so no push of a handled article reads waiting for ever. The own push keys join the same two batched reads (no extra query). A course or product never gets a mark from a `push:` row once the time is removed (a course is not an article under today's rule).
- **Docs.** The warnings are replaced with the plain statement that removing the variable returns the page to today's rule and nothing is reposted: `docs/LINKEDIN_POSTING.md` ("Every push posts" bullet and the switch-over step 3), `docs/FACEBOOK_POSTING.md`, `.env.example` (all three variables). `docs/BACKUPS.md` is unchanged (its "restore time or unset" advice is about a restore, where the `push:` rows are gone).

### Deviations and notes (planning please review)
1. **One earlier test of mine changed on purpose.** The Channels test "both times unset … no push key is ever queried" asserted a property this follow-up gives up: with the times unset the batched reads now also carry each ARTICLE's own `push:` key (that is how a removed time still shows the row's status). It now asserts that only an article's own push key is queried, never a course's. No test file other than `socialAllPushes.test.ts` was edited.
2. **"Any push of the article" has one consequence worth knowing:** an article whose oldest push is before the all-pushes time and has no row yet (waiting, say), but one of whose repeats ALREADY has a `push:` row, is not posted by today's rule (the page already has the article through the repeat). In normal order this cannot happen while the new rule is on (candidates go oldest first, so the oldest push is handled before its repeat), so it only matters after a removal, which is the point of the guard.
3. **Channels sees an article's other pushes only inside the list it is building** (the newest 600 campaigns on Campaigns, the short list on the Dashboard). The screens' 15-day window holds all of an article's pushes; an older push outside a Campaigns list is not seen, so a push whose only `push:` row belongs to a push outside the list reads waiting. Rare, and only after a removal.
4. **A same-row resend is still shown once** (open point from the first report, unchanged).
5. The guard reads only keys that start with `push:`; nothing in the schema or the row shape changed. No index was added: `LinkedInPost` / `FacebookPost` have no `campaignId` index, and the screens' `OR` filters one page's rows by campaign id; the tables are small (about 60 posts a day per page) and I did not measure it.
6. **Moving the time EARLIER can still repost** (not in the brief, not built). The pushes between the two times were handled under today's rule (article-key rows) and become new-rule candidates with new `push:` keys, so each would post once more. The docs say to set the time to the moment of switching on, never earlier. A guard cannot simply skip a push whose article key already has a row, because acceptance 5 of the first build requires a repeat of an already-posted article to post again; it would need the moment the variable was first set, which is not stored. If wanted: a one-line docs warning, or a small change that stores that moment.
